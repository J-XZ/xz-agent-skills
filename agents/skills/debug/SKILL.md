# 实证调试

入口从项目文档和脚本发现。

## 流程

1. **记录基线**：保存失败命令、退出码、关键错误、环境及触发条件，确认已有改动和可修改范围。
2. **缩小复现**：构造保留故障机制的最小负载；并发或分布式问题保留必要的时序、节点和数据规模。
3. **取得证据**：先读日志、堆栈、转储和指标；不足时使用匹配的调试器或最小临时插桩。构建失败直接以真实命令输出取证。
4. **确认根因**：连接触发条件、错误路径与实际缺陷，区分相关和因果。无法稳定复现时使用已有现场证据；仍不足则报告不确定性和最小补证步骤。
5. **最小修复**：只修改证据指向的路径，沿用项目风格和现有能力。
6. **验证**：复跑最小复现、原失败路径及必要回归。偶发问题按失败频率和预算确定重复次数。
7. **清理交付**：移除本次插桩和临时进程，恢复实验配置；说明根因、证据、改动、验证和限制。

## 取证要求

- 选用对应运行时的调试器、性能分析器或追踪工具；原生程序使用匹配符号。性能和竞态问题保持代表性的优化级别。
- 附加调试器前确认目标进程及影响范围，考虑暂停和插桩对时序的扰动。
- 插桩只覆盖待验证路径，带本任务唯一标记；热路径优先采样或聚合。
- 每轮只收集能区分假设的信号。多次修复在同一点失败时，先验证它们的共同前提。
- 没有新证据时换定位方法，而不是叠加补丁。

## 边界

- 优先增量构建和相关测试；缺少环境或权限时如实报告。
- 共享服务、用户数据和生产环境操作须在授权范围内。
- 只恢复本次改动，保留用户工作；清理失败时列出残留。
- 单独使用时自己完成；在多代理协作中沿用外层分配的角色。默认不提交、不推送。
