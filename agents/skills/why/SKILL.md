# 设计缘由调查

代码只证明当前行为，作者意图需要历史证据。用户提出的原因按待验证假设处理。

## 调查

1. 明确代码、决策及时间范围；仅解释当前行为时使用 `how`。
2. 阅读相关源码、调用点、测试和文档，确认当前行为与约束。
3. 按需使用限定文件的 `git blame`、`git log` 和 `git show` 追溯来源；涉及重命名时使用 `git log --follow -- <file>`。设计来源可能早于最近一次修改。
4. 核对提交说明、设计文档及可访问的相关讨论，检查后续撤销、替代和冲突证据。已有材料足够时停止。
5. 引用实际核查的文件位置、提交 ID 或链接；历史缺失时说明调查范围和证据缺口。

## 证据等级

| 等级 | 表述要求 |
| --- | --- |
| 直接证据 | 记录明确说明原因，写明来源；该理由是否正确、是否仍适用需单独判断。 |
| 间接支持 | 多项独立证据支持同一解释，列出依据。 |
| 推断 | 从事实推导但缺少历史记录，说明依据和限制。 |
| 猜测 | 仅在有助于回答时提出可能解释，明确尚无证据。 |
| 未知 | 说明查过什么、缺少什么。 |

## 边界与交付

- 直接只读调查，不修改文件、不运行构建或测试、不改变 Git 状态。
- 外部查询限于问题所需的授权来源。
- 并列呈现冲突证据，分别说明当前行为、历史理由和当前建议。
- 先给结论及证据等级，再列关键依据和未知项。
- 调查为后续修改做准备时，列出需保留的约束和待确认风险，由用户决定是否实施。
