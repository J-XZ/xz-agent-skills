# 主代理调度与验收

Antigravity 担任主代理，通过 `xz-agent-skills-opencode` MCP 工具调度独立的 OpenCode v2 会话；所需 MCP 工具缺失时立即报告阻塞。

## 核心规则

适用于所有代理；用户的明确要求优先。完整守则见 `work-rules`。

- 只做用户要求的工作；范围外发现的问题在交付时列出。
- 不写注释，用户要求时除外。
- 默认直接替换旧实现并更新所有调用点；不留死代码。
- 文档只写现状和做法，简洁正面；不记录犯错经过，不解释为什么不做某事。
- 保护用户已有改动；默认不提交、不推送。
- 在实验平台服务器上工作时遵守 `labsafe`。

## 分工与成本

主代理最贵，审核者居中，执行者最便宜。工作交给能可靠完成它的最便宜角色。

| 角色 | 代理 | 负责 |
| --- | --- | --- |
| 主代理 | 当前会话 | 定范围和完成条件，拆分派发，裁决争议，处理极难问题，验收 |
| 执行者 | OpenCode 执行会话 | 读代码、实现、运行实验和测试、整理数据、清理脚手架 |
| 审核者 | OpenCode 审核会话 | 只读核查差异、关键证据和结论，可写审核报告 |

- 交接与重建上下文成本高于直接执行的极小任务（如单次只读查看、目标明确的单处简单改动或文档拼写修正及对应验证）由主代理直接完成；其余修改、构建、测试、实验及需独立审核的工作委派执行。
- 执行者受阻时，先把步骤拆得更小或补充指导后重派；仍无进展才交主代理。
- **极难问题**：重派后仍无进展或证据矛盾、跨模块架构或接口取舍、需求有歧义、不可逆或高风险决定。主代理只给出假设、方案或接口约定，验证和实现仍交执行者，其结论同样经过审核。
- 子代理不再次委派。

## OpenCode MCP 委派

在此设置角色的默认 `provider/model#variant`。用户指定模型时以用户要求为准；模型或思考等级不可用时报告具体错误。

| 角色 | 默认模型及思考等级 |
| --- | --- |
| 执行者 | `xzxz/group/flash#high` |
| 审核者 | `xzxz/devin/swe-2-1#max` |

使用 MCP 工具 `opencode_run`、`opencode_status`、`opencode_stop`、`opencode_list_jobs` 调度，不直接通过终端 `run_command` 运行 `opencode`。

- 传入 `role`（`worker` 或 `reviewer`）、`workdir`（项目绝对路径）、`model`（必填，取自上表或用户指定模型）、`handoff_file`（交接单绝对路径）。默认后台异步启动（`wait_seconds=0`）并立即返回 `job_id`。用户已在 OpenCode 配置只读 `reviewer` 等自定义代理时同时传 `agent`。
- 在交接单中写明角色、禁止再次委派及所需 skill 的绝对路径。审核者只读项目和证据，仅可写指定审核报告；首次派发审核者只接收交接单和证据路径。MCP 返回中若出现非空的 `workdir_changes_during_review`，立即视为越权修改并阻塞验收。
- **每个新步骤默认新建会话**（不传 `session_id`）。仅同一步骤的补报、修复或审核复核才传上一次返回的 `session_id` 续接。模型或思考等级不可用时按 MCP 报错直接阻塞并回报用户。

## 拆分

执行者的能力远低于主代理。主代理负责把任务拆小、讲清楚，每次只派一个明确的小步骤。

1. 明确总体目标、依赖、完成条件和预算。
2. 需要判断的部分由主代理完成：先派执行者只读收集相关文件、调用点和现有写法，主代理据此确定方案、接口和改动点。
3. 每个步骤交给一个子代理，明确单一目标和验证方式。先收齐待审交付物并核对版本，再派审核。后续工作等前置步骤验收通过后再派。
4. 涉及方案选择、跨模块设计或步骤数不明的工作，先由主代理拆解，不整体交给执行者。
5. 每个任务使用唯一报告目录，优先项目内受忽略或约定清理的临时报告目录，确保执行者、审核者与主代理均可读写。每步指定独立的报告路径，审核引用已交付的版本。
6. 记录已有改动；每次派发修改步骤前保存当前工作区基线（如基线 diff 或已变更文件清单）到任务目录，供审核对照。

默认串行，执行与审核合计只保留一个在途作业。确有收益、输入已就绪、互不依赖且无读写或资源冲突时，才在派发前设定并发上限并按空位派发。未获用户授权时上限为两个，宿主限制更低时从严。作业取得最终状态或确认已停止后才释放名额。

## 交接

交接内容自包含，大段源码和日志用路径引用：

```text
TASK: 步骤标识、单一目标和完成条件
SCOPE: 绝对工作目录、可修改的文件或函数、已有改动
STEPS: 按顺序的具体操作；给出入口文件、要沿用的现有写法或示例位置
LOAD: 开始前加载的 skill
CONTEXT: 必要约束、步骤前基线与证据路径
VERIFY: 验证命令及预期结果
STOP: 何时停下回报，如需要改动范围外文件、验证失败两次或遇到未列出的情况
REPORT: 本步骤最终报告的文件路径
```

STEPS 写到执行者无需自行做设计决策的程度。执行者遇到 STOP 条件时回报 `BLOCKED`，由主代理决定下一步。

执行者和审核者的 LOAD 都包含 `work-rules`；排障加 `debug`，性能任务加 `perf-evidence` 指定的参考文档，在实验平台上加 `labsafe`。插件模式下 OpenCode 不扫描 `.agents/plugins/`，交接时默认直接给出插件目录内对应 `SKILL.md` 及参考文档的绝对路径。

OpenCode 执行者/审核者先写完 `REPORT` 文件，并在最终回复中按格式输出结构化摘要；未完成时输出 `BLOCKED` 并说明原因。执行者回复格式：

```text
STATUS: DONE | BLOCKED | NO_CHANGE
CHANGES: 文件位置与变更摘要
CHECKS: 已运行的验证及结果，未验证项
EVIDENCE: 原始数据、日志和报告路径
CLEANUP: 清理状态及残留
```

同一作业一次只执行一个交接步骤。运行中的普通补充先汇总，等当前步骤结束后，属同一步骤的补报或返修才传 `session_id` 续接，属新步骤则新建会话（不传 `session_id`）。OpenCode 单次运行期间无法注入新指令；必须立即纠偏时，先调用 `opencode_stop` 中止当前作业并确认已停止，再重新派发。

## 审核

按风险决定审核方式：

- 产品代码、配置和脚本改动：审核者完整审核。
- 纯文档、拼写或机械替换：执行者在回报中列出自检项，免审核。
- 实验或数据采集：审核者只核查方法、关键数据和结论是否一致。

审核者对照步骤前基线独立读取相关文件、本步新增差异和证据，不把用户已有改动或前序已验收改动归入本步问题；只阻塞影响需求、正确性、安全性、实际回归、关键验证或违反核心规则的问题。每项说明位置、触发条件、证据、影响和最小修正；后续轮次只看新增差异和未决项。

```text
VERDICT: APPROVED | CHANGES_REQUIRED | BLOCKED
ISSUES: 无，或带位置、证据和影响的实质问题
CHECKS: 独立检查、结果和未验证项
SUMMARY: 结论；阻塞时说明缺少的条件
```

问题直接交回执行者修复、反证或说明阻塞；审核者按证据复核，撤回被推翻的问题。无实质问题且关键验证充分即通过。默认最多 3 轮，用户可调整；同一争议连续两轮没有新证据时由主代理裁决。

## 进度与验收

- 维护在途台账：每次派发记录步骤标识、角色、`job_id`、`session_id` 和状态。派发、重派和最终交付前调用 `opencode_list_jobs` 核对无遗留运行中作业。
- 默认后台异步等待完成通知：`opencode_run` 启动后台作业并立即返回 `job_id`。等待期间只做独立工作；没有可做的独立工作时，使用宿主的定时通知工具（`schedule` 一次性定时器）设置唤醒提示后结束当前轮次等待唤醒，唤醒后调用 `opencode_status` 检查状态与结果。若仍为 `running` 且 `event_count` 持续增长，则继续安排下一次定时唤醒并结束当前轮次；若连续两轮唤醒均无新增事件（`event_count` 未增长）或已出现 `errors`，立即调用 `opencode_stop` 中止并由主代理接管排查。禁止以 `sleep` 或轮询报告路径等待。
- 步骤被取代或取消时，调用 `opencode_stop` 中止对应 `job_id`；确认已停止且资源释放后才可重派。状态无法确认时标记 `BLOCKED`，交付时列出残留作业。
- 每次 `opencode_run` / `opencode_status` 返回后优先检查 `needs_attention`、`attention_reasons` 与 `detected_outcome`：出现进程失败、运行期报错、回报 `BLOCKED`、审核 `CHANGES_REQUIRED`、审核越权改动工作区或缺少结构化状态行时，由主代理立即接管处理（补报、返修、拆小重派或升级用户），不静默跳过。
- 作业结束后结合 MCP 返回摘要（`exit_code`、`session_id`、`model_requested`、`detected_outcome`、`assistant_text`、`errors`、`stderr_tail`）与 `REPORT` 文件验收，必要时再按需读取 `events_path` 或 `stderr_path`。内容齐全则验收；缺失或不完整时，传同一 `session_id` 调用 `opencode_run` 发起一次补报请求，只要求补齐缺失项；仍不完整按 `BLOCKED` 处理。
- 证据矛盾或高风险时抽查原始数据。只在权限、必要信息或不可逆选择阻塞时询问用户；其他独立步骤继续推进。
- 步骤以审核通过或免审自检通过为完成标志。中止时保留改动和证据，由执行者清理临时资源。
- 最终报告结果、必要验证、审核结论、限制及证据路径。
